## S2: Gapless MediaSource playback

Scripts: `spikes/m0/s2_make_chunks.py` (chunk sets plus a pytest for the EBML splitter) and `spikes/m0/s2_player.html` (served at `http://localhost:8765/s2_player.html?set={sine|speech}&variant={A|B|C}`).

**Setup:**
- Sets A and B use standalone WebM/Opus chunks (48 kbps, 48 kHz, mono). Each chunk is encoded separately, and every file has its own EBML header and init.
  - `sine`: a 440 Hz sine at 0.3 amplitude, cut into 3 × 10 s chunks (30 s total).
  - `speech`: the first 90 s of `out/s3_gpu.wav`, cut into 3 × 30 s chunks.
  - In every chunk the container is 8 ms longer than the audio (10.008 s and 30.008 s). The extra comes from the Opus pre-skip (312 samples) plus padding to a full frame.
- Variant A: `sequence` mode, chunks appended in order.
- Variant B: `segments` mode, with `timestampOffset` plus `appendWindowStart/End` set per chunk from the manifest durations.
- Variant C (`sine-c`, `speech-c`) is the spec 6.5 fallback.
  - One continuous Opus encode per set (`ffmpeg ... -f webm -live 1 -cluster_time_limit <chunk ms>`), split by an EBML walk into a 457 B `init.webm` plus 4 cluster media segments. All of them are appended in order to one SourceBuffer in `segments` mode, with no offsets or windows.
  - Clusters are cut about 19 ms early: they start at 0, 9.981, 19.981 and 29.981 s (speech: 0, 29.981, 59.981, 89.981 s). This leaves a 19 ms tail segment.
  - The concatenated `init + seg-*` decodes offline to exactly 1,440,000 samples (sine) and 4,320,000 samples (speech).
- Browser for the automated checks: Chrome/152 (Claude desktop browser pane). UA: `Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Claude/2.37337.1 Chrome/152.0.7977.130 Safari/537.36 MSIX`.

**Automated `window.__s2` results** (pass = one buffered range, start < 0.05 s, |end − total| < 0.05 s):

| Set | Variant | pass | buffered end | expected | Note |
|---|---|---|---|---|---|
| sine | A | false | 30.063 | 30.000 | per-append ends 10.021 / 20.042 / 30.063 → +21 ms per chunk |
| sine | B | true | 30.0000 | 30.000 | |
| speech | A | false | 90.063 | 90.000 | |
| speech | B | true | 90.0000 | 90.000 | |
| sine | C | true | 30.021 | 30.000 | |

Caveats (from the task review, recorded as rulings):
- B's pass is forced by the structure of the test: `appendWindowEnd` clips each chunk to its manifest duration. So the pass flag says nothing about sample continuity.
- A must be judged by its per-append +21 ms deltas, not by the 0.05 s boolean.
- WebM timestamps are rounded to 1 ms, so B can be at best ±0.5 ms accurate at each boundary.
- The per-chunk `samples` values in the C manifest are approximate because they come from 1 ms-rounded cluster timestamps. A production worker must read the cut points from the muxed stream.

**Sample-level capture** (controller; MediaElementSource → ScriptProcessor at 48 kHz). The expected maximum sample-to-sample step for the 0.3-amplitude 440 Hz sine is 0.0173.
- **B at 10 s and 20 s: a real splice glitch.**
  - maxJump was 0.514, with 244 jumps > 0.03 spanning 993.5–1027.3 ms of the capture window (about 34 ms).
  - The RMS dipped to 0.0128 for 1 ms (steady level 0.212).
- **Offline ffmpeg decode plus concat of the same three A/B chunks: clean.**
  - The maximum step was 0.0186, with no dip.
  - So the encoding is fine. The glitch comes from how Chrome's MSE handles independently encoded WebM streams.
- **C, boundary 1 (9.981 s): clean.** At 1x, maxJump was 0.0173 with 0 jumps. At 1.5x, maxJump was 0.0174 with 0 jumps.
- **C, boundary 2: inconclusive.**
  - A no-boundary control at 5.0 s showed the same 8-jump dropout pattern.
  - This means the ScriptProcessor capture itself drops samples when the main thread is under load.

**S2 verdict:**
- Neither the plan's "A PASS" nor its "B PASS" holds, because both variants click audibly at chunk boundaries. Under the plan's rules, the outcome is **FAIL → shared-init media segments**.
- That fallback was validated in this spike as variant C: **C PASS**.
  - The owner heard no click at any real boundary, for both sine and speech.
  - The sample capture was clean at boundary 1.

Controller ruling: the production player uses one continuous Opus encode per chapter. A shared init segment plus the cluster media segments are appended in order to one SourceBuffer.

Carried to M3:
- Build a sample-continuity test based on AudioWorklet, because ScriptProcessor capture is unreliable.
- The worker keeps one encoder open per chapter and reads the cluster cut points from the muxed stream.

| VieNeu temperature parameter | `temperature` (default 0.8 in v3 Turbo `infer`). `infer` has no seed parameter. | S3 |

| Segment quality guard | VieNeu output noise varies per sample and per preset. The worker measures the 4-12 kHz / 0-4 kHz energy ratio in vowel frames per segment and re-synthesizes outliers (max 2 retries). | S1 debug |
| Playback continuity test | M3 adds an AudioWorklet-based sample-continuity test on a sine fixture (ScriptProcessor capture proved unreliable). | S2 |
| Cluster cut points | ffmpeg cuts clusters about 19 ms before `-cluster_time_limit`. The worker reads cut points and timestamps from the muxed stream and never assumes cluster N == text chunk N. | S2 |
| onnxruntime pin | The `.venv-cpu` spike env keeps onnxruntime 1.24.4 pinned (it did not fix the load error). | S3 |
